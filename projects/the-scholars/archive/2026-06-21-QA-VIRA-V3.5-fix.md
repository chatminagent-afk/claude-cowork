## DETAIL TEMUAN

### 1. 🔴 `Update Buffer` salah kunci pencocokan (akar masalah debounce)
- `Update Buffer` (appendOrUpdate) `matchingColumns = ['No WA']`, isi `No WA = user_wa` (= `body.from` mentah).
- Semua node STATS lain mencocokkan pakai `lid`. Node `Process Counter & Merge Data` malah menulis `No WA = user_phone` (digit di-strip; **kosong** untuk user @lid).
- Akibatnya untuk user **@lid**: `body.from` = "...@lid" ≠ `No WA` di baris (kosong) → appendOrUpdate **menambah baris baru** tiap pesan → STATS duplikat, `Re-Read STATS Debounce` (filter lid) jadi ambigu, perbandingan timestamp di `IF_Chat_Debounce` bisa salah → pesan bisa "hilang".
- Lookup `pending_msg` di dalam `Update Buffer` juga cari baris pakai `No WA === user_wa` → untuk @lid gagal → riwayat `pending_msg` tidak terakumulasi (multi-bubble pecah).
- **Rekomendasi:** ganti `matchingColumns` `Update Buffer` ke **`lid`**, dan ubah lookup internal `pending_msg` agar pakai baris hasil `Read User STATS` (sudah terfilter lid) — bukan dicari ulang via `No WA`. Jadikan `lid` satu-satunya kunci di seluruh node; `No WA` cukup informatif.

### 2. 🔴 `Rate Limiter` bucket global
- Inputnya dari `Update Buffer` (output node Google Sheets: field `No WA`, `pending_msg`, `timestamp`, `lid` — **tidak ada** `user_wa`). Kode `const userWa = input.user_wa;` → `undefined` → key `rl_undefined`.
- Semua user berbagi satu bucket → batas 5 pesan/menit berlaku untuk seluruh trafik, bukan per user.
- **Rekomendasi:** ganti ke `$('Chat Counter').first().json.user_lid` (atau `user_wa`) sebagai key.

### 3. 🔴 `HITL Check` tidak berfungsi + tidak ada re-check pasca-wait
- `const input = $input.first().json;` berasal dari `Read STATS for HITL` (read tanpa filter → baris pertama sheet). `input.user_lid`/`input.user_wa` **undefined** → `find` by lid gagal → `botMode = ''` → selalu lanjut. Node ini efektif tidak pernah mem-block.
- Gerbang HITL yang benar-benar bekerja adalah `IF Bot Mode Active` (baca `Read User STATS` terfilter lid) — tapi posisinya **sebelum** `Wait3` 60 dtk. Jika Sam set `bot_mode=OFF` selama 60 dtk debounce, tidak ada pengecekan ulang yang valid → bot tetap membalas.
- **Rekomendasi:** (a) perbaiki `HITL Check` ambil `user_lid` dari `Chat Counter`; (b) pindahkan/ tambahkan re-check HITL **setelah** `Re-Read STATS Debounce` (yang sudah terfilter lid) supaya toggle Sam saat window debounce dihormati.

### 4. 🟠 Debounce 60 detik
- `Wait3.amount = 60` detik, padahal komentar di `Cek_user_status` menyebut "Wait 8 detik". Ditambah `Wait1` (random 5–10 dtk) sebelum reply → total ~65–70 dtk sebelum user dapat balasan.
- **Rekomendasi:** turunkan debounce ke ~8–12 dtk (sesuai komentar awal) kecuali 60 dtk memang disengaja. Sinkronkan komentar.

### 5. 🟠 `gform_sent_ts` tidak ter-stamp
- Sejak pengiriman GForm dilakukan inline di `Process All` (inject URL), satu-satunya node yang menulis `gform_sent_ts` (`Update GForm Sent TS1`) hanya disuplai oleh node **nonaktif** `Send GForm Link` → tidak pernah jalan.
- Fitur "follow-up otomatis bila form belum diisi" biasanya bertumpu pada `gform_sent_ts`; tanpa stamp, scheduler follow-up tak punya acuan.
- **Rekomendasi:** saat `isSendGForm` true di `Process All`, set flag agar `gform_sent_ts` ditulis ke STATS (mis. lewat cabang update kecil yang match `lid`).

### 6. 🟡 Whitelist masih aktif
- `IF (Whitelist)` membatasi ke 5 nomor (`6285155202354`, `6281510624599`, `6596110395`, `6589200455`, `628176480658`) dan workflow `active=True`. Cek lewat `body.from` — untuk user @lid pun tak akan match.
- **Rekomendasi:** konfirmasi ini memang fase uji. Nonaktifkan/lepas whitelist sebelum go-live publik.

### 7. 🟢 Housekeeping
- `user_code` & `secret` Kirimi hardcoded plaintext di `Reply Chat Kirimi`, `Notify Talk to Sam`, dll. Sebaiknya pindah ke n8n Credentials (HTTP Header Auth) agar tidak ikut tersimpan di file JSON yang dibagikan.
- Node mati: `Update GForm Sent TS1` (tak terjangkau), cabang `Process All → IF Send GForm` (nonaktif). Bisa dirapikan.
- `pinData.Webhook` masih ada — hapus sebelum finalisasi agar tak membingungkan.
- Blok `_DEBUG` di `Process Counter & Merge Data` dan komentar basi ("Wait 8 detik") sebaiknya dibersihkan.
